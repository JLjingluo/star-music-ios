Star Music 0.6.0（构建 8）安装包审查与修改清单

一、审查范围与结论说明

审查对象：StarMusic-Unsigned 3.ipa。

本次已检查：
1. IPA 文件结构。
2. Info.plist 应用配置。
3. 隐私清单。
4. 程序中的类型、函数符号和接口线索。
5. 内置界面文案与错误提示。
6. 音频录制、播放、转换和渲染相关接口。
7. CREPE 模型配置、输入输出规格与资源。
8. 项目保存、导入导出、编辑与撤销相关实现线索。

审查限制：
这是编译后的 IPA，并非完整源码，且本次没有运行 iOS 应用。因此，不能把潜在风险写成已经复现的 Bug，也不能仅凭安装包判断实际页面是否存在遮挡、重叠、动画卡顿或间距错误。

以下内容区分三种状态：
【确认】安装包可以直接核实的配置、行为说明、限制或问题。
【风险待验证】存在具体功能或实现线索，但需要源码审查或运行测试确认。
【设计建议】用于改善界面和交互，不等同于已经发生的程序错误。

严重程度按问题触发后的用户影响划分：
重：可能丢失创作、错误覆盖内容、破坏项目或导致核心流程失败。
中：明显影响操作、理解、兼容性和产品体验。
轻：文案、一致性、视觉细节和交付品质问题。

不得把下面所有条目都当成“已经证实存在的 Bug”。其中待验证条目应先复现、定位，再决定是否修改。


二、重度问题与高优先级验证项

重 01：保存失败后，最新编辑可能只保留在内存中

状态：
【确认存在内存保留提示；是否存在额外恢复机制待验证】

证据：
包内存在：
“当前编辑仍保留在本次运行的内存中。返回草稿后也可重新打开重试；请勿强制退出或删除应用。”
并能看到 unsavedProjects、EditorSession.persist 和紧急导出项目包等实现线索。

问题：
用户仍能看到最新作品，不代表最新作品已经落盘。iOS 可能在后台终止进程，用户也可能误以为返回草稿就是保存成功。

验证步骤：
1. 编辑已有草稿。
2. 通过可控方式制造保存失败。
3. 返回草稿列表，再打开项目。
4. 将应用切到后台，再终止进程。
5. 冷启动检查最新修改是否存在。

修改要求：
1. 正式保存失败时，尽可能保存可恢复快照。
2. 不能假定空间不足时，在同一磁盘另存就一定成功。
3. 启动时识别未提交版本，提供恢复入口。
4. 持续区分“正在保存”“已保存”“保存失败”。
5. 紧急导出必须使用最新内存版本。
6. 如果内容完全无法落盘，明确显示哪些修改尚未保存。

验收标准：
不能在重启后无提示地用旧版本替代用户最后看到的版本。


重 02：项目元数据和原始录音可能只保存成功一部分

状态：
【风险待验证】

证据：
应用使用独立录音目录 StarMusic/Recordings，并通过 ProjectStore 管理项目。

风险场景：
1. 音频复制成功，项目保存失败。
2. 项目保存成功，音频复制失败。
3. 导入工程中途退出。
4. 最近删除恢复项目时，音频未同步恢复。

影响：
草稿看起来存在，但原声无法播放，重新识谱、裁剪和完整备份失效。

修改要求：
1. 使用临时区域准备项目及音频。
2. 提交前检查音频依赖是否完整。
3. 失败时回滚本次新增内容。
4. 启动时检测缺失引用。
5. 音频缺失必须明确报错，不能以静音伪装成功。
6. 清理孤立音频前，考虑最近删除、撤销历史和恢复快照。

验收标准：
在保存、复制和导入过程中终止应用，重启后得到完整项目或明确失败状态。


重 03：异步识谱结果可能覆盖等待期间的用户修改

状态：
【风险待验证】

证据：
应用支持异步识谱，并明确说明重新分析会替换所选音轨音符。

验证场景：
1. 对音轨 A 开始识谱。
2. 等待期间修改 A。
3. 切换到音轨 B。
4. 删除 A。
5. 切换到另一个项目。
6. 等待旧任务返回。

潜在错误：
1. 结果写入当前选中的 B。
2. A 的新修改被旧结果覆盖。
3. 已删除音轨被错误恢复。
4. 结果写入其他项目。

修改要求：
1. 任务绑定项目 ID、音轨 ID、音频来源 ID。
2. 记录开始任务时的项目或音轨修订号。
3. 返回时验证目标仍存在。
4. 目标已修改时，结果作为候选，不直接覆盖。
5. 应用识谱结果必须是一次完整的可撤销操作。

验收标准：
切轨、删轨、切项目和继续编辑，都不能造成旧结果误写。


重 04：取消分析后，任务可能仍提交结果

状态：
【风险待验证】

证据：
存在任务取消接口和“取消分析，保留原录音”入口。不能据此认定没有取消机制，但还需验证取消是否覆盖结果提交阶段。

验证场景：
1. 请求已返回、尚未完成解析时取消。
2. 本地模型推理过程中取消。
3. 取消旧任务后立即启动新任务。
4. 连续点击完成或重新分析。

影响：
用户已经取消，音符仍突然变化；较慢旧任务覆盖较快新任务。

修改要求：
1. 每个任务分配唯一标识。
2. 取消后撤销该任务提交结果的资格。
3. 推理循环、解析完成和写入前均检查取消状态。
4. 同一目标只有当前有效任务可以提交。

验收标准：
取消后等待足够时间，项目不得再被该任务修改。


重 05：草稿覆盖写入可能发生损坏或旧版本覆盖新版本

状态：
【风险待验证】

证据：
能看到 ProjectStore.save，但无法仅凭符号确认原子保存和版本保护策略。

验证场景：
1. 写入期间终止应用。
2. 磁盘空间接近耗尽。
3. 连续拖动音符，密集触发保存。
4. 保存期间撤销或切换项目。

修改要求：
1. 单项目保存串行化。
2. 使用临时文件和原子替换。
3. 保存带修订号。
4. 禁止旧修订覆盖新修订。
5. 保留至少一个已知可读取的历史版本。
6. 避免每次细微拖动都完整重写大工程。

验收标准：
异常退出后至少保留一个完整版本，且不能无提示回退。


重 06：大文件与音频处理中间副本可能造成内存峰值过高

状态：
【确认输入限制和内存数据接口；实际超内存问题待验证】

已知限制：
1. 音频文件最大 256 MB。
2. 项目包最大 512 MB。
3. 单次分析最长 5 分钟。
4. 成品导出最长 10 分钟。

实现线索：
存在以 Data 处理工程导入、以 Float 数组处理采样、返回 WAV Data 的接口。

问题：
文件体积上限不等于运行内存上限。解码、混音、编码和复制可能同时占用多份数据。

参考计算：
1. 5 分钟、16 kHz、单声道 Float32，单份采样约 19.2 MB。
2. 10 分钟、44.1 kHz、单声道 Float32，单份采样约 105.8 MB。
3. 中间副本与编码输出会继续增加峰值。
4. 若工程以 Base64 封装音频，还需要考虑额外体积；具体封装方式尚未确认。

修改要求：
1. 导入前检查体积、解码时长和声道数。
2. 分块解码、混音和写出。
3. 限制工程累计音频体积和音符数量。
4. 导出时避免构建不必要的完整副本。
5. 失败不能破坏现有工程。

验收标准：
在最低支持设备上测试接近上限的工程，记录峰值内存和完成情况。


重 07：改变 BPM 后，原声与音符可能失去同步

状态：
【确认行为限制；实际错位待验证】

证据：
“BPM 不改变原声音高，也不自动拉伸原声。”

问题：
原声按真实秒数播放，音符可能按拍数和 BPM 播放。二者混用时，改变 BPM 可能只改变音符时序。

验证场景：
1. 让原声与乐器轨对齐。
2. 把 BPM 从 120 改到 90。
3. 检查试听和导出是否逐渐错位。

修改要求：
1. 区分修改节拍参考与修改播放速度。
2. 明确显示受影响的内容。
3. 未实现时间拉伸时，不暗示整首同步变速。
4. 保存来源音频与工程时间的映射关系。

验收标准：
界面、试听和导出使用一致的时间规则。


重 08：裁剪原声后重新识谱可能出现起点偏移

状态：
【风险待验证】

场景：
原音频 30 秒，只分析 10～20 秒，模型返回 startSeconds=0.5。

问题：
0.5 秒通常是片段内部时间，不能直接当成完整原声或工程时间。

潜在错误：
1. 音符错误放到工程开头。
2. 对应原声试听跳错位置。
3. 多次裁剪后偏移重复累加。
4. 改变 BPM 后再次错位。

修改要求：
明确区分：
1. 来源音频时间。
2. 分析片段内部时间。
3. 工程时间。
4. 节拍位置。

验收标准：
裁剪、识谱、移动、改 BPM、保存重开后，音符仍能定位到对应原声。


重 09：模型 JSON 返回值的业务校验可能不足

状态：
【确认有 JSON 提示词；校验完整性待验证】

可能异常：
1. MIDI 超范围。
2. 起点或时长为负数。
3. 超大时长或过量音符。
4. 数字字段返回字符串。
5. 不合理的重叠音符。
6. 返回解释文字、代码块或截断 JSON。
7. 返回无法接受的非有限数值。

影响：
可能导致谱面尺寸异常、导出占用过高或当前工程被污染。

修改要求：
1. 提示词不能代替客户端校验。
2. 限制音符数量和时间范围。
3. 检查数值类型、范围及有限性。
4. 处理超出原声长度的结果。
5. 全部验证成功后再提交音轨替换。

验收标准：
异常模型响应不得改变当前工程。


重 10：录音中断后的界面与实际录音状态可能不一致

状态：
【确认有中断和路由处理；正确性待验证】

已发现：
1. 音频中断通知。
2. 音频路由变化通知。
3. 中断后暂停并要求主动继续的文案。

验证场景：
1. 麦克风权限弹窗期间切后台。
2. 来电后拒接。
3. 拔耳机或蓝牙断开。
4. 暂停期间再次中断。
5. 达到录音时长上限。
6. 连续点击继续录音。

潜在问题：
界面显示录制中，实际没有写入；计时增长但文件未增长。

修改要求：
1. UI 由实际录音器状态驱动。
2. 恢复失败时保持暂停。
3. 使用实际录音时长校验计时。
4. 中断后通过明确操作恢复。

验收标准：
任何状态下，界面显示与实际录音行为一致。


重 11：复制、删轨和撤销可能破坏音频依赖关系

状态：
【风险待验证】

验证步骤：
1. 复制项目 A 为 B。
2. 删除 A。
3. 在 B 删轨并撤销。
4. 导出并重新导入 B。
5. 清理最近删除。
6. 检查 B 的全部原声。

潜在问题：
复制项目仍依赖原项目音频；撤销只恢复音符，没有恢复来源关系。

修改要求：
1. 明确音频独立复制或不可变共享策略。
2. 按引用关系删除音频。
3. 撤销覆盖音符、音轨、配器和来源关系。
4. 完整备份前检查依赖。

验收标准：
复制工程能够独立备份、恢复和继续编辑。


重 12：试听和导出可能使用不同状态或不同声音规则

状态：
【风险待验证】

验证场景：
1. 导出后立即改音符。
2. 导出中改变静音或独奏。
3. 原声与乐器轨混合。
4. 播放中切换项目。
5. 取消导出后重试。

修改要求：
1. 导出采用明确的项目快照。
2. 试听与导出共用时间、混音、静音、独奏和裁剪规则。
3. 旧渲染结果不能在新播放请求后启动。
4. 完成状态对应实际成功生成的文件。

验收标准：
同一项目状态的试听和 WAV 文件，在内容与时序上保持一致。


三、中度问题与交互改进项

中 01：社区主体功能尚未接入

状态：
【确认；功能缺口】

现状：
真实账号、发布、关注、评论和消息尚未接入，目前是本地创作工具加社区演示。

影响：
用户进入相关页面后不能完成期待中的操作。

修改建议：
1. 当前突出创作和草稿。
2. 社区明确标注示例。
3. 未完成能力在进入操作前说明。
4. 避免让用户操作到最后才发现功能不可用。


中 02：“发布”若只导向未接入提示，会形成操作死路

状态：
【确认存在未接入提示；实际入口呈现待验证】

修改建议：
1. 当前使用“分享音频”或“导出”。
2. 在线功能实现后再加入“发布到社区”。
3. 明确项目包、MIDI、WAV 的用途。
4. 不把导出与社区发布混为同一任务。


中 03：系统文档类型声明不完整

状态：
【确认配置缺失；系统表现待验证】

证据：
开启文件共享及原位打开支持，但未发现 CFBundleDocumentTypes 和 UTExportedTypeDeclarations 等声明。

影响：
应用内能导入，不代表在“文件”或聊天附件中点开工程时能自然交给 Star Music。

修改要求：
1. 声明自有工程格式。
2. 仅注册真正支持的文件类型。
3. 测试从文件、邮件和分享面板进入。
4. 外部导入也处理重复操作和失败回滚。


中 04：“简洁、普通、专业”模式差异不直观

状态：
【确认模式存在；设计问题】

问题：
简洁和普通概念接近；工具复杂度与视图类型可能混在一起。

修改建议：
1. 名称表达实际差异。
2. 将图形视图和五线谱视图作为独立显示切换。
3. 说明切换不会删除内容。
4. 不必强行保留三个难以解释的层级。


中 05：“声音”一词指代多个不同对象

状态：
【确认文案混用】

涉及：
删除这个声音、添加声音、只听这个声音、选择一种声音。

问题：
可能分别指音符、音轨、音色和录音。

修改建议：
1. 音符统一称一个声音片段。
2. 音轨统一称一条旋律或音轨。
3. 音色统一称乐器声音。
4. 原声统一指录制音频。
5. 删除操作明确对象和范围。


中 06：“整首换调”与部分原声不变存在理解冲突

状态：
【确认限制存在】

修改建议：
1. 有未转谱原声时，说明只调整可编辑旋律。
2. 标出受影响音轨。
3. 原声不变时不能笼统承诺整首一起变化。
4. 试听和导出保持相同规则。


中 07：分段换乐器会创建声部，需要提前解释

状态：
【确认该行为】

风险：
1. 反复操作导致音轨增加。
2. 用户误以为原轨音符丢失。
3. 新轨名称和选择状态不清楚。
4. 接近轨道上限时失败。

修改建议：
1. 操作前说明会创建新音轨。
2. 完成后选中新轨并突出显示。
3. 整体操作一次撤销。
4. 合并相同配器时保留来源关系。


中 08：跨小节处理要求新手做专业判断

状态：
【确认相关选项存在】

问题选项：
后移到下一小节、保留跨小节延音。

修改建议：
1. 默认尽量保留听感与时间位置。
2. 通过合适记谱表达跨小节时值。
3. 必须选择时提供短试听或示意。
4. 明确说明后移会推迟起音。


中 09：自由节奏、量化和 MIDI 导入需要统一时间语义

状态：
【确认功能存在；正确性待验证】

需要区分：
1. 保留实际播放时间。
2. 保留原始节拍与速度变化。
3. 吸附当前工程网格。

修改要求：
1. 导入时说明策略。
2. 量化可以撤销。
3. 可比较处理前后听感。
4. 使用变速 MIDI 检查导入和再次导出。


中 10：“专业五线谱”能力需与名称匹配

状态：
【风险待验证】

检查项：
1. 升降号和还原号。
2. 延音与跨小节音符。
3. 附点、休止和同时发声。
4. 高低音加线。
5. 密集音符排版。
6. 拖动位置与实际 MIDI 音高。
7. 换调后的记谱正确性。

修改建议：
若仅提供简化谱面，明确名称和能力边界。

五、整体界面修改方向

1. 创作首页
突出最近草稿和“录制旋律”。
导入、空白创作作为次级入口。
减少首屏说明文字。

2. 录音页
突出实际录音状态、计时和波形。
主要操作为开始、暂停、完成。
引擎、节拍等设置放展开区域。
明确原声是否已经保存。

3. 处理页
区分正在保存原声、正在分析和正在提交乐谱。
取消操作应清楚说明是否保留原声。
不使用虚假的精确进度。

4. 编辑页
主体留给旋律、音轨和播放位置。
播放控制保持稳定。
量化、配器和重新识谱放工具区。
保存状态持续可见。
切换模式不改变项目内容。

5. 导出页
项目包：用于完整备份和继续编辑。
MIDI：用于其他音乐软件编辑旋律。
WAV：用于直接收听和分享。
高级参数不抢占主要入口。

6. 示例与社区
当前明确标注演示内容。
突出试听和创建独立改编。
未接入发布、评论和消息时，不让用户进入操作死路。

7. 底部导航
底部标签表示稳定的页面区域。
录音、发布和新增等动作通过页面按钮或工具栏触发。
不把页面导航和执行动作混为一类。

苹果设计参考：
https://developer.apple.com/design/human-interface-guidelines/tab-bars


六、建议修复顺序

第一优先级：
保存与恢复、项目与音频完整性、异步识谱防覆盖、取消后禁止提交结果。

第二优先级：
原声与音符时间映射、BPM 行为、裁剪偏移、试听与导出一致性、大文件内存。

第三优先级：
文件类型注册、API 配置与错误提示、音轨操作和撤销关系、横竖屏与 iPad。

第四优先级：
模式和术语统一、页面信息层级、社区演示入口、无障碍、配色和玻璃效果。

第五优先级：
细节文案、按钮反馈、发行包处理和兼容性说明。


七、执行要求

1. 待验证问题必须先复现或检查源码，不能直接判为已存在 Bug。
2. 修复不能破坏已有原声、草稿、来源关系和撤销能力。
3. 数据完整性优先于视觉美化。
4. 界面修改优先采用清楚的层级、稳定布局和系统交互。
5. 每个确认问题记录触发步骤、实际结果、预期结果和修复验证。
6. 实际页面的遮挡、间距、文字截断、色彩对比和动画问题，需要运行画面进一步确认。另外还有一个特别特别重要的问题，就是生成的那些可能就是生成的音符，有时候会出现乱码，并且并不清晰。
